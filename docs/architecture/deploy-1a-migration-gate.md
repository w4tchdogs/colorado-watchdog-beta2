## Authentication from an empty owner state

Discovery and listing return schemas without Website-account authorization when the Worker has D1. Each protected call resolves the principal through the Website account service, rechecks the live role and requires `d1.inspect` in both the handler and inspection service. Missing D1 returns HTTP 503, including for discovery. Missing, malformed, invalid, expired or revoked bearer credentials deny access. An explicit invalid bearer has no human fallback. A valid insufficient role is denied, and Agent Owner is explicitly rejected. The current Worker has no verified hosted human provider. Native Sites MCP documents viewer authentication at the transport boundary. Hosted delivery of a separate Website bearer and preservation of its semantics at that boundary remain to be verified. A Sites viewer identity or a published capability declaration provides no Website authorization.

From an unverified owner state there is no current Website-account issuance authority. The existing account API requires an authorized current principal to create the agent and issue a key. AUTH-3 owns provider selection and a verified runtime identity path. AUTH-4 owns a separately authorized, attributed first-owner procedure. The current bootstrap is tied to the native Sites provider and fixed logical project/binding, requires the append-only audit introduced in 0014, and insists on the entire contiguous, exact-checksum application ledger through **0017** at the assessed commit. An 0014-only schema or 0014 plus later schema with 0015 held cannot satisfy it. Any AUTH-4 adaptation needs verified target identity, a provider-bound subject, the 0014 audit, explicit validation of the approved held schema, and the existing atomic first-owner safeguards. An authentic signed-in human with no linked account still has no issuance authority.

After those dependencies, an authorized human can use the existing account service to create a dedicated agent and issue an expiring credential through the same-origin account API. Issuance returns the secret once in a no-store response and persists its hash, expiry and an attributed audit event. Deliver it privately to the trusted MCP caller via an approved secret store or credential channel. Send it only over TLS to the verified endpoint, retain identity/expiry references for audit, and exclude the secret from logs, transcripts, GitHub and tool parameters. Revoke the identity through the version-checked account API, audit the revocation, and verify the old key is denied. Hosted issuance and delivery remain unverified.

Agent Administrator is the lowest current role that passes the inspection gate. It also receives account, identity, checkpoint, banner and report capabilities on other surfaces. A short expiry and a read-only MCP tool catalog leave those privileges on the bearer. Before distributing an inspection credential, introduce a bounded `d1.inspect`-only account or credential grant through the existing service and enforce that limit across the dashboard/API/MCP surfaces. The current Administrator fixture proves local authorization behavior only.

The app runner requires a contiguous exact history, and the current MCP comparison expects the full contiguous catalog. Retain only bounded outcome counts and unresolved reasons in MCP, with private evidence handled through the approved service. Verify foreign keys and the full relationship inventory, including indirect references. Compare stable per-relationship counts and private fingerprints of identifier-to-FIPS mappings before and after on the isolated restore.
3. Use a Sites-supported consistent snapshot/export of the exact Website D1 or a documented write-quiescence window covering the database and execution evidence. Record the source and snapshot identity, commit point, format, UTC time and SHA-256. Store encrypted with controlled access outside GitHub. Include the deployed artifact and binding metadata as separate recovery dependencies. Restore to a fresh, isolated database with a distinct verified identity, disconnected from production writes and credentials. Verify the backup digest and compare schema and indexes, the platform execution snapshot and application history, all 64 pairs, dependent fingerprints and counts. Require integrity check success and zero foreign-key violations. Where the supported interface cannot run these checks, require equivalent evidence from the verified isolated restore. Smoke-test the matching Worker and protection boundaries with synthetic credentials. A saved Worker version does not restore D1. Stop on conflicting identity, stale snapshot, missing material, restore failure or indeterminate integrity. [Cloudflare D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)
4. Leave 0015 held until the migration, identity, credential and recovery evidence agrees. If a future isolated test returns an ambiguous publish or migration outcome, suspend activation/retry and reconcile both ledgers and schema against the known snapshot first. Post-application verification must establish exactly one recorded execution, an exact final registry, unchanged FIPS keys and dependents, and an intact recovery trail before any later production step.

The four existing MCP tools expose bounded summaries, the application's migration ledger, two target county names and allowlisted relationship counts with suppression. Remaining gaps include trusted physical binding identity, platform execution evidence, the complete 64 pairs, verified historical assignment, complete dependent-reference integrity and backup/restore proof. `state: ready` means the inspection queries returned. It can accompany a missing or invalid ledger. Use the detailed history and independent evidence for the gate. Keep any new inspection methods fixed, bounded and capability-guarded.

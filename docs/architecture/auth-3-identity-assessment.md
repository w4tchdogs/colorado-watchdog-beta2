# AUTH-3 — Verified hosted human identity assessment

Assessed November 14, 2026 against main at `8c03d31c08d2c5f97b03d8b40fa225799c3f0dbd`, after the DATA-3 and DEPLOY-1 assessment merges. Alpha-1 is public and its recorded deployment predates this source. The assessment used source, documentation and local checks. No hosted sign-in, private account, production credential, domain change, deployment or owner bootstrap was involved.

## Recommendation

Choose **Auth0 Free with a first-party Regular Web Application, RS256 and a GitHub social connection** if the owner accepts GitHub accounts for the initial staff group. This gives the Worker a signed assertion it can validate independently of Sites ingress. Auth0 and GitHub offer free plans. The design uses the existing Site origin, the default Auth0 tenant hostname and Website D1. It adds no email, SMS, custom auth domain or separate hosting service. The sizing assumption is a small staff cohort, well below 25,000 external monthly active users. Public readers and anonymous grievance reporters don't need an identity-provider account. This is a $0 design under current published terms, subject to the hosted fit checks below and future plan changes. Use only verified opaque subjects. Names, email, GitHub usernames, organization membership and provider claims about roles grant no Website authority. Provider account and tenant deletion, recreation, changing issuer domains and upstream account linking can change the subject. An operator must verify control of the new subject and authorize an audited relink. Keep a subject tombstone where applicable under the approved retention policy. Revoke local access immediately, then handle deletion of eligible local and provider records separately from security audit retention. Disclose the providers, data flows, consent scopes, deletion contacts and retention before launch. Keep provider credentials, authorization codes, JWTs, cookies and subject identifiers out of URLs where avoidable, browser storage, analytics and logs. Callback URLs temporarily carry an authorization code and state, so suppress query logging and referrers and redirect immediately to a clean URL.

## Worker trust boundary

Sites documents auth-enabled Sites, HTTPS-capable server hosting and separate visitor connections. The installed reference exposes native runtime secret configuration. Cloudflare documents Worker HTTPS `fetch` and Web Crypto RSA verification. This establishes runtime primitives, not an Alpha-1 acceptance test. Confirm that its gateway forwards the Worker-owned `/auth/*` route, callback query and cookies, accepts `Set-Cookie`, and allows bounded HTTPS calls to the chosen token and key endpoints. Use the actual browser-visible canonical origin, pinned in trusted configuration. The reserved Sites `/callback` stays platform-owned. Connected-app consent, workspace membership and the SIWC service bypass token provide no Website human principal. [Sites data and connections](https://learn.chatgpt.com/docs/sites/data-and-connections) · [Worker Fetch](https://developers.cloudflare.com/workers/runtime-apis/fetch/) · [Worker Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)

For built-in Sites sign-in, require a documented authenticated context or a signed, site-bound assertion, or a documented exclusive ingress that strips client identity headers on every path and injects a stable site-scoped subject only for authenticated visitors. Establish coverage of public, preview, custom-domain, service and any alternate or direct Worker ingress before enabling this path. A hostname match or observing successful sign-in cannot prove ingress isolation. Verify the deployment contract with OpenAI, then confirm it with a disposable isolated Site and synthetic users before trusting the boundary. If the platform supplies a signed assertion, pin its issuer, audience, key source and lifetime. Otherwise Sites owns callback/state/nonce, session and logout and must document their relevant guarantees. Keep the native adapter without a context in the meantime.

### External OIDC flow

1. Initiate a top-level redirect from the canonical origin, with random nonce, state and S256 PKCE. Keep a short-lived, single-use transaction in D1 bound to a separate opaque host-only browser cookie. Allowlist relative return destinations and use a fixed issuer, client and redirect URI. No URLs derived from request authority or forwarded headers.
2. On GET `/auth/callback`, validate the host, method, response parameters, transaction and browser binding. Reject missing, conflicting and duplicate parameters. Atomically consume the transaction before exchanging the code over HTTPS using the stored verifier and server-held client secret. Reject error responses and absent ID tokens. Use a maintained Worker-compatible verifier. Allowlist RS256 and pin issuer, client audience and key endpoints. Check the signature, exact `iss`, `aud`, `azp` when applicable, `exp`, `iat`, optional `nbf` and required matching `nonce`, with a small bounded clock tolerance. Reject ill-formed or duplicate claims, empty subjects, ambiguous keys and untrusted token key URLs. Cache trusted JWKS for a bounded period, coalesce refreshes and refresh once on a legitimate key miss subject to rate limits. Deny if verification fails or trusted keys are unavailable. [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html) · [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700) · [Auth0 key rotation](https://support.auth0.com/center/s/article/Tenant-Signing-Key-Rotation)
3. Use the exact `sub` under a fixed provider namespace based on the configured issuer, separate from `chatgpt-sites:<site-id>` and `agent-key`. Require a unique live link to an active human account before issuing a privileged session. Generate a fresh opaque random handle, store only its hash and binding to the identity/account in D1, and use a `__Host-` cookie with Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain. Apply those cookie properties to the short-lived transaction too. Discard provider tokens after validation. Set both idle and absolute limits, renew only within the absolute window, and require fresh upstream authentication at expiry. Initial proposed bounds for owner review are five minutes for a transaction, 30 minutes idle and at most eight hours absolute. Use no refresh tokens. Track the session's issuer and issuance time for incident revocation. Consider shorter limits or fresh authentication for sensitive actions.
4. Resolve the server-side session and recheck its exact link and current account on each protected request. Prevent a username, account ID, second cookie, or changed provider subject from selecting a different account. Keep account APIs' same-origin mutation checks, audit all other cookie-authenticated writes and reject missing or foreign origins. Use a per-session CSRF token for browser writes where exact Origin alone can't cover the surface. Apply no-store to auth responses and private pages. Local logout uses same-origin POST, revokes the server session and clears its cookie. Explain that upstream SSO can remain active and test fresh login and optional provider logout. A stolen valid cookie remains a bearer credential until expiry or revocation. Local link revocation and account disable take effect on subsequent requests. Upstream-only revocation can lag until local absolute expiry and fresh authentication. Provide an operator invalidation path for compromised keys, tenants and sessions.

## Threat and mitigation matrix

| Threat or failure | Required behavior |
| --- | --- |
| Missing identity, caller headers, alternate or direct Worker access | External mode requires a Worker-verified session on the canonical origin. Ignore claimed Sites identity, forwarded host and role headers. Native mode remains disabled absent verified provenance on every ingress path. |
| Forged, wrong-issuer, wrong-audience, malformed, conflicting or expired token | Reject before any local session or account lookup. Fail closed on unknown keys, ambiguous claims, unexpected algorithms and stale key material. |
| Login CSRF, callback replay, mix-up and open redirect | Single issuer, exact redirect, browser-bound one-use state, S256 PKCE, nonce and local bounded return path. Reject duplicate params. Concurrent callbacks permit at most one successful consumption. |
| Session fixation, account substitution or cross-site write | Rotate handles at sign-in, use exact session-to-identity binding, reject ambiguous cookies, recheck active D1 identity and enforce same-origin writes. Make authorization checks using the current principal for the requested resource. |
| Role elevation, unlinked subject, inactive account or revoked link | No automatic account, link or role creation. Require a unique active human link. Keep D1 role/capability rechecks and owner protections. Version and audit identity changes. |
| Malformed or invalid Authorization header plus valid human session | Existing strict agent-key branch remains authoritative when Authorization is present. Invalid, expired, duplicated or revoked agent credentials deny with no human fallback. Valid agent credentials retain only their own D1 permissions. A Sites bypass remains transport access only. Preserve MCP capability checks and any route-specific restrictions on caller kind. |
| Provider failure, D1 failure or key incident | New logins fail cleanly without falling back to headers. Existing local sessions obey live D1 checks and expiry. D1 failure denies privileged access. Operator can invalidate all affected sessions and disable human auth without disabling public reads or existing agent auth. |

## Integration and subsequent implementation assignment

- **Sites adapter.** Keep `createSitesIdentityAdapter` and its site-specific namespace. Supply `VerifiedSitesContext` only if the owner selects the native route and hosted provenance is established. Confirm whether the required email field is always present or make it optional metadata. In external mode implement a distinct `HumanIdentityAdapter` for the verified session.
- **Worker and D1.** Add one explicit provider selection, disabled by default, on the intended Site and canonical origin. Document public config, secret names and the kill switch. Add Worker-owned start/callback/logout routes and a minimal isolated Website D1 migration for transactions and sessions if external OIDC is selected. Use D1 atomic consumption, bounded cleanup and tests for concurrent callback and revoked sessions. Existing accounts, identities, role matrix and audit schema remain authoritative. Wire into `createD1AccountServices`, require human kind in the human branch and verify binding to the persisted identity. Check current dependency constraints before choosing a verifier with no Node-only runtime requirement.
- **Protected surfaces.** Update the hardcoded ChatGPT sign-in prompt in `account-admin.ts` and other affected entry points to the selected route. Preserve JSON denial, same-origin checks, audit and capability checks across account API, staff/report and MCP. Review which programmatic routes permit cookies versus require agent keys. Never widen route capabilities as part of wiring authentication.
- **Bootstrap and invites.** Existing `bootstrapFirstOwner` hardcodes the native Sites provider and project. Preserve project/database/schema checks, atomic single-owner protections, attributed audit and idempotence. AUTH-4 must bind a verified provider namespace and opaque owner subject using a trusted operator procedure independent of public login. An unlinked callback creates no privileged session or accounts. AUTH-5 owns time-limited invitation proof, identity binding, and role assignment under D1 authorization. Neither operation belongs in the AUTH-3 sign-in callback.
- **Test the chosen path.** For external OIDC add generated key/token fixtures for valid and invalid signature, algorithm, issuer, audience, authorized party, times and nonce. Cover key rotation and outage; callback CSRF, query ambiguity, malicious return destinations, expiry and concurrent replay; session fixation/substitution, logout replay, duplicate cookies, role demotion, wrong-kind account, revoked link, disabled account and missing links. Cover agent precedence with absent, malformed, duplicate, unknown, valid and revoked keys, plus cross-origin writes and direct requests without a session. For native mode replace the OIDC-specific tests with the verified context contract, identity omission, alternate ingress and service access checks. Run full repository checks and Worker tests.
- **Hosted gate after selection.** Start with a disposable isolated Site and synthetic principals. Confirm the existing audience can stay public, runtime secrets/egress, canonical callback, cookie behavior on a default Sites hostname, current consent scope, rotation and logout. Show a locally linked, deliberately low-privilege fixture can sign in and that an unlinked one cannot. Keep logs limited to outcome codes. Use a test binding, and coordinate production deployment with DEPLOY-1 and D1 migration provenance. If the external callback or cookie contract fails, obtain the smallest supported equivalent from OpenAI before proposing another service or hostname. Roll back by disabling the human adapter and revoking affected sessions.
